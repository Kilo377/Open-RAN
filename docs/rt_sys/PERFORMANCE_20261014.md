# 2026-10-14：优先处理运行成本

本轮只做耗时定位和一个现有候选筛选的独立配置验证，不重跑长承载矩阵，不修改既有数据。大规模运行成本仍未解决。

## 测量方式与结果

Spark GB10 GPU 串行运行，两个地图各 3 小区、24 UE、静止、8 slots、初始每 UE 1000 字节、seed=512。每个工作进程独立启动，概率缓存为空；两个反馈模式使用相同部署和外生到达。此夹具用于冷启动成本诊断，不代表空队列承载测试、稳态速度或移动场景。阶段计时在边界同步 CUDA；link_total 包含其子阶段，不能重复相加。首次使用的信道缓存状态不同，实测信道读取/计算仅约 0.04–0.23 秒，不解释主要差异。

| 地图 | 实际 NR 参考 | 缓存统计模式 | 实际 NR + 容量筛选 | 相对原实际 NR |
|---|---:|---:|---:|---:|
| Street | 57.98 s | 85.55 s | 38.13 s | 1.52 倍 |
| Munich | 172.27 s | 274.48 s | 85.20 s | 2.02 倍 |

原实际 NR 模式中，Street 的 AMC/BLER 探针约 44.89 秒、波形查找/构建约 8.11 秒，112 次实际发送 TB 的反馈约 0.69 秒；Munich 分别约 152.31、14.42、0.67 秒。两地图探针占总时间约 77% 和 88%。缓存模式的探针/准入占约 89% 和 94%。当前模式名称中的“实际 NR”仍包含大量 Monte Carlo 探针，不能理解为每个实际发送 TB 只解码一次。

## 已验证的改进

独立配置 `configs/rt_sys/nr_reference_screened.json` 开启已有 `reference.information_screening`。它利用当前等效独立高斯资源假设下的信息量上界和 Fano 必要条件，排除不可能达到目标 BLER 的候选 MCS；没有降低解码迭代数、样本预算或 RT 精度，实际发送仍通过 NR 编解码产生 ACK/NACK。默认配置不变。

Street 的解码试验从 33,200 次降至 21,744 次；Munich 从 79,406 次降至 34,286 次。两个夹具分别逐行比较 192 条记录，调度、MCS、ACK、TB 字节、交付字节和反馈来源均无差异；初始环境指纹和非空到达事件一致，资源、功率、队列和有效载荷审计通过。本地回归为 252 passed、1 skipped、2 subtests。

这是两个短夹具的结果一致性与耗时改进，不保证所有种子、信道或长时间运行逐位一致，也不等于完整规模性能验收。新增配置文件会改变覆盖全部配置文件的源码指纹；数值 Python 实现没有修改。各执行版本及输入配置保存在快照中。

可使用该配置运行独立实际 NR 测试，并为每次运行选择新的输出目录：

```bash
.venv-spark/bin/python experiments/run_rt_sys.py \
  --scene munich --cells 3 --ues 24 --slots 8 --seed 512 \
  --ue-speed-mps 0 --initial-queue-bytes 1000 \
  --feedback-mode nr_tb_reference \
  --config configs/rt_sys/nr_reference_screened.json \
  --output outputs/my_screened_reference_run
```

## 尚待实现的主要优化

容量筛选只能减少无效候选，保留了每时隙的 AMC 和独立 BLER Monte Carlo 探针。下一步需要独立、明确的执行模式：MCS 使用可用的延迟测量及已返回 ACK/NACK 做因果链路自适应；实际每次发送保留真实 NR 解码；BLER 从实际反馈统计；Monte Carlo 探针仅用于独立抽查。该模式尚未在本轮实现，不能把预期加速当成实测结果，也不能未经验证继承原参考模式的目标 BLER 声明。重传仍须保留同一码字与资源兼容性检查。

新模式应先检查反馈时序、实际解码次数、HARQ/队列守恒、吞吐与 BLER，再逐步扩大到移动和长时间实验。阶段计时中的实际 TB 时间只是一个组成部分，不能直接据此推算完整仿真加速倍数。

原始性能数据在 `outputs/rt_performance_20261014/`，结构化分析为本目录 `performance_20261014.json`，附逐文件 SHA256 清单。既有 `final_ran` 完整验收归档保持不变。
